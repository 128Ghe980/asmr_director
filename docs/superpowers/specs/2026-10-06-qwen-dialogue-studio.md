# Qwen dialogue studio

Date: 2026-10-06

The user requested a standalone web page that turns a story brief into dialogue for a chosen number of speakers, assigns saved reference voices, and generates a complete scene. The initial delivered example is the eight-line historical scene **雨渡送药**, voiced by `normal_zh` and the stable **正太音2** reference ID `user-dd2a4e32-e72d-4e80-bf7d-96611831b52b`.

## Runtime and contract

- All new code, cache, temporary files, and outputs live under `I:/AI/qwen3-tts-dialogue`; page port7866 binds only127.0.0.1.
- A lightweight server reads the existing planner API URL/key/model configuration server-side. Credentials remain outside browser responses, logs, and saved outputs. Only the story brief and dialogue requirements are sent to the text API.
- Story generation returns a validated title,1–8 characters with unique IDs, and2–24 ordered turns. Each turn has a unique ID, character foreign key,1–250-character text, and bounded emotion/intensity/tempo enums. API output cannot choose files or TTS parameters.
- The user can edit dialogue, assign each character an existing reference, preview references, choose seed and0–1500ms pauses, then submit a frozen synthesis snapshot. API generation is a separate explicit action from synthesis.
- The server submits individual lines through the existing7864 Gradio `/run_one` endpoint, using graft mode, Chinese, normal voiced delivery, and a512-token ceiling. It does not load a second GPU model. The existing Qwen queue serializes this page and the community page.
- One dialogue synthesis is active at a time. Cancellation stops between turns; the current upstream turn can finish. Already generated clips are preserved. Failed/cancelled jobs expose available partial clips and a clear status.
- A separate resume action creates a new job from an unfinished job only when story, bindings, and options exactly match. It verifies the completed contiguous prefix against saved WAV/JSON hashes, reference hashes, and actual parameters, copies the original bytes, and generates only missing turns. The source job remains unchanged. Memory failures stop with a diagnostic; recovery never automatically restarts the worker.
- Original per-turn WAV/JSON files are copied unchanged into a job folder. Mono24kHz PCM16 clips are concatenated with sample-count-based pauses; no volume normalization. Combined WAV, UTF-8 dialogue, timed SRT, and provenance manifest are downloadable.
- The browser persists editable drafts and job IDs in localStorage and restores recent results from the server. Editing makes an old result visibly stale while preserving playback. No autoplay and only one audio player is active.

## Fixed-instruction and single-line extension

The subsequent user feedback was that instructions worked but voice consistency was too low. The requested extension adds fixed instructions per character and one-line regeneration; it does not establish that the resulting voices are perceptually more consistent.

- `options.strong_consistency` is a strict boolean, defaulting to false for old requests and manifests. `options.character_instructions` maps current character IDs to complete instruction strings. With the mode on, every character requires an effective 1–250-character nonempty string. Leading/trailing whitespace is normalized once, internal line breaks are retained, and the same complete effective string is passed for every line by that character without appending per-line emotion/intensity/tempo. Turning the mode off retains browser drafts while excluding them from effective option comparison; normal per-line delivery resumes.
- Effective snapshot comparison ignores per-line delivery in fixed mode and inactive instruction drafts in normal mode. Legacy history and localStorage without the new fields remain compatible. Fixed instruction drafts follow stable character IDs, survive reload, and do not expose model/API credentials.
- A reroll request uses `reroll_job_id`, `reroll_turn_id` and `reroll_seed` together; it cannot also request resume. The source must be a complete scene with all ordered clips. Only the target line's text and effective delivery may change. Character data, voice bindings, target speaker/ID, other effective lines, order/count and effective global options must match. Global changes require a full scene generation.
- The target seed is an independent integer from0 to2147483647; it does not modify the global seed or other clips' actual seeds. The browser requires a seed different from the target's previous actual seed and proposes `(old_seed + 1) % 2147483648`. Direct API calls may reuse the seed for revised text/reproducibility. `planned_turn_seeds` preserves mixed actual seeds and any unfinished target seed through later rerolls/resume; public results expose each clip's actual seed.
- Source copied/original WAV and JSON hashes, metadata parameters, current reference hashes and frame counts are verified before reuse. The worker proceeds in turn order: unchanged clips are copied byte for byte, only the target calls the upstream generator, and all clips receive freshly calculated sample offsets, gaps and SRT timing. A new job/folder retains its provenance; the source job remains unchanged.
- Whole-scene, resume and reroll tasks use the same job gate and upstream queue. A failed/cancelled target retains only the completed contiguous prefix; no later copied clip is published as a completed prefix. Resume uses the persisted per-turn seed plan. No automatic model restart, normalization of audio or extra GPU model is introduced.
