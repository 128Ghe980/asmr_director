# 项目管理规则

Last updated: 2026-06-26

这份文件只记录项目协作与续写规则，不记录具体产品路线。具体产品路线只看 `docs/ROADMAP.md`。

## 1. 单一路线来源

- `docs/ROADMAP.md` 是顶层产品路线的唯一硬来源。
- `docs/AI_HANDOFF.md` 只做上下文恢复摘要，不能定义另一套路线。
- `docs/project-archive.md` 只做历史记录，不能覆盖当前路线。
- Agent 不能凭直觉新增顶层路线步骤。
- 实现细节不能被升级成新的顶层路线关卡，除非用户明确批准修改 roadmap。

## 2. 回答“下一步是什么”之前必须检查

每次用户问下一步、路线、优先级、是否继续某个方向时，agent 必须先检查：

1. `docs/ROADMAP.md`
2. `docs/AI_HANDOFF.md`
3. 当前 git status
4. 最近提交或最近项目记录

回答必须基于“固定路线 + 当前项目状态”，不能当场编一个新步骤。

## 3. 路线必须结合项目现实

- 遵循 roadmap 时，也要检查当前代码、文档、运行状态是否已经发生变化。
- 如果现实状态显示原计划不足、过时、或需要调整，agent 必须说明原因，并先提出 roadmap 修改建议。
- 在用户确认前，不得直接改变顶层路线。
- 用户最新的明确指令可以覆盖文档，但覆盖后要把相关文档更新到一致状态。

## 4. 文档留档

每完成一个有意义的项目步骤，必须更新适当文档：

- `docs/ROADMAP.md`: 当前步骤状态、验收进度、路线变更。
- `docs/AI_HANDOFF.md`: 给后续 AI / 上下文压缩后的恢复摘要。
- `docs/project-archive.md`: 已完成工作的历史记录与关键决策。

重要 spec 需要同时保留英文版和中文版，避免后续 AI 只看到一半语境。

## 5. 完成声明必须有证据

- 声称完成、修复、可用、通过之前，必须运行与改动相称的验证。
- 如果是文档改动，至少检查文件存在、关键引用正确、没有明显互相矛盾的旧说法。
- 如果是代码改动，需要运行相应测试、typecheck、lint、构建或手动验证。
- 如果某项验证没跑，要明确说明原因和剩余风险。

## 6. Git 节奏

- 重要里程碑稳定后，优先整理文档、提交、推送，再进入新的大步骤。
- 不要把不相关改动混入同一次提交。
- 如果工作树里有用户或其他 agent 的改动，不要擅自 revert；必须先识别范围，再协同处理。
