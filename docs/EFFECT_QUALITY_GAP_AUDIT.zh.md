# 初版效果质量差距审计与完善顺序建议

更新时间：2026-07-13

状态：交接分析，尚未批准为新 roadmap

适用对象：接手本项目的 AI / 开发者

## 1. 文档目的

固定十步 roadmap 已全部完成，项目已经具备可运行、可编辑、可本地生成、可混音、可试听、可导出 WAV、可保存多项目和版本恢复的工程闭环。

但这个闭环主要证明了数据契约和产品骨架可以贯通，不代表最初设想中的“AI ASMR 导演”已经达到可用的声音质量。本文件盘点：

1. 哪些能力已经是可信底座，应继续复用；
2. 哪些实现是为了跑通初版而采用的明确兜底；
3. 哪些部分与最初设计仍有明显距离；
4. 下一阶段建议按什么顺序完善，避免继续把基础桥接误当成效果进展。

本文件不是 `docs/ROADMAP.md` 的替代品，也没有创建“第 11 步”。后续对话必须先和用户确认新的顶层目标，再把获批范围写入 roadmap / spec。

## 2. 核心结论

当前版本更准确的定位是：

> 一个已经打通真实本地音频生成与工程管理链路的 AI ASMR 工作台骨架，但导演指令、声音质量、音效素材、空间处理和自动质检仍大多处于初版或兜底水平。

项目没有“白做”。最难替换的工程底座已经存在：Timeline DSL、统一 Clip/Asset 契约、生成任务状态、稳定资源 URI、真实 WAV 混音、项目库、版本、波形分析和可折叠工作区。后续应在这套契约上升级声音引擎，不应重新搭一轮 mock、bridge 或页面外壳。

真正的优先问题也不是继续增加工作台面板，而是：

> 让界面上的声音导演指令真实、可听、可比较地改变声音，并让语音、音效、空间和母带的质量进入可验收状态。

## 3. 已经可靠的底座

以下能力不属于兜底，应保留并继续扩展：

- `AsmrProject` / Timeline DSL 是 UI、校验、生成、混音和导出的统一数据源。
- Clip 生成已经贯通 `queued -> generating -> succeeded / failed / canceled` 的状态模型，运行时任务不会污染项目 JSON。
- 最终音频使用稳定的 `asset://clip/...` 和 `asset://mix/...` 引用，可播放、分析和下载。
- GPT-SoVITS 已接入本地语音生成；非语音 Clip 也走相同的资产契约。
- 项目混音会按时间线、音量、淡入淡出、位置和移动信息生成真实立体声 WAV。
- 本地项目库、迁移、复制、删除、自动保存、最多 12 个恢复版本和混音指纹已经建立。
- 真实 WAV 波形、采样率、声道、峰值和 RMS 分析已经接入。
- 左右侧栏可折叠，中间 Timeline 可以获得足够空间；当前 UI 方向可继续使用。
- 测试覆盖了关键领域逻辑。Step 10 完成时为 29 个测试文件、184 个测试通过，lint 与 webpack build 通过。

这些能力意味着后续可以更换或增加语音、音效、音频编辑和空间处理 provider，而不必推翻产品状态模型。

## 4. 明确的兜底实现

### 4.1 导演指令只是确定性 JSON 参数修改

当前 `更柔`、`更近`、`左耳`、`右耳`、`停顿`、`降低` 并不是 AI 音频修改：

- `更柔`：主要把 `volume_db` 降低 2 dB，并写入风格元数据；没有对音色、气声、语气或频谱做真实处理。
- `更近`：设置 `distance: "very_close"` 并降低 1 dB；在混音端“距离”目前基本只是增益映射。
- `左耳` / `右耳`：修改 pan 和 distance，属于普通声像参数。
- `停顿`：在文本末尾追加 `" ..."`，不是结构化停顿或可控的语音韵律编辑。
- `降低`：只降低音量。

证据：`apps/web/src/lib/asmr/director-presets.ts:17`、`:69`、`:73`、`:96`。

影响：按钮名称表达的是声音意图，但实现只是在修改元数据或基础参数，容易让用户误以为发生了模型级音频编辑。

### 4.2 GPT-SoVITS 没有消费多数导演语义

当前请求会使用 Clip 的文本，但 `emotion`、`style`、`pace` 没有映射到 provider 能理解的控制方式；关键参数仍是固定值：

- `temperature: 1`
- `speed_factor: 0.86`
- `seed: -1`

证据：`apps/web/src/lib/asmr/gpt-sovits-provider.ts:45`、`:52`、`:57`、`:59`。

影响：即使 Inspector 中的风格或情绪字段发生变化，重新生成的声音也可能基本不变。当前参考音频为日语、目标内容为中文，跨语言 zero-shot 已能听清，但实际测试质量仅为一般。

### 4.3 呼吸、摩擦、敲击、环境声是程序噪声合成

`breath`、`sfx`、`ambience` 当前由随机噪声、包络、滤波式数值处理和脉冲合成，不是素材库检索，也不是生成式音效模型：

- 呼吸：噪声配合吸气/呼气包络；
- 摩擦：摩擦噪声分支；
- 敲击：脉冲式分支；
- 雨声：连续噪声底加稀疏滴落脉冲。

证据：`apps/web/src/lib/asmr/procedural-audio.ts:133`、`:154`、`:190`。

影响：能证明多类型 Clip 的生成、播放和混音链路，但缺少真实材质、微观变化、近讲录音细节和可持续循环质量。原设计明确要求“授权音效库优先 + AI 生成补充”，见 `docs/asmr导演早期设计.md:388`。

### 4.4 空间处理是单声道折叠、等功率声像和距离增益

当前渲染会先把来源左右声道平均成 mono，再通过等功率 pan 写回立体声；距离主要映射为 gain。还没有：

- 距离相关 EQ；
- 早期反射；
- 双耳微延迟；
- 房间混响发送；
- HRTF / binaural convolution；
- 对真实立体声素材的保留策略。

证据：`apps/web/src/lib/asmr/project-mix-renderer.ts:214`、`:257`、`:296`。原设计对 pan、gain、EQ、混响和微延迟的要求见 `docs/asmr导演早期设计.md:193`。

影响：“更近”与“更远”主要表现为大小声，不具备接近耳边、离开耳边或跨耳移动应有的频谱、相位和空间感。

### 4.5 `target_lufs` 不是严格的 LUFS 母带

当前实现把 `target_lufs` 数值近似转换为目标 RMS，仅在电平偏低时做有限提升；limiter 是样本硬截断，并非真峰值检测、软限制或响度标准化。

证据：`apps/web/src/lib/asmr/project-mix-renderer.ts:332`、`:334`、`:345`。

影响：导出的音频技术上可用，但响度一致性、瞬态、失真控制和平台发布适配还不能称为正式母带。

### 4.6 进度与取消只是桥接层近似

本地生成进度使用固定阶段百分比，不能反映 provider 的真实工作量；取消是客户端 best effort，GPT-SoVITS 请求发出后通常不会被真正中断。

影响：不妨碍初版本地运行，但长任务时的反馈和资源控制不可靠。它是运行体验问题，不应继续被包装成核心效果里程碑。

### 4.7 当前“质量检查”是工程就绪检查，不是听感质检

质量面板现在检查 schema、资源是否齐全、混音是否新鲜、WAV 是否可分析、声道和峰值余量。它尚未检查：

- ASR 转写是否与目标文本一致；
- 漏字、重复、乱码和异常停顿；
- 时长是否偏离 Timeline；
- 同一角色跨 Clip 的音色一致性；
- 人声是否被雨声或音效遮蔽；
- 爆音、静音、削波、噪声和伪影；
- 失败后自动重试或候选优选。

原设计把自动质检列为独立模块，见 `docs/asmr导演早期设计.md:457`。

### 4.8 产品入口和 Timeline 编辑仍是 demo 级

- 首页直接加载固定 `demoProject`，没有“一句创意 -> 结构化脚本 -> Timeline”的创建流程。
- Timeline 能选中和查看，但缺少完整的新增、删除、替换、排序、拖拽、播放头和范围编辑。
- 项目列表是浏览器本地存储，不是文件系统项目包；尚无资产清理和迁移工具。
- 当前主要导出真实 WAV 和项目 JSON；MP3、stems、SRT、发布包仍未完成。

这部分与最初产品形态的差距见 `docs/asmr导演早期设计.md:9`、`:124`、`:570`、`:584`、`:643`、`:644`、`:928`。

## 5. 与最初设计相差最远的能力

按差距而非开发难度排序：

1. **一句创意自动形成工程**：没有 LLM planner、脚本拆分、情绪节奏规划、音效建议和自动 Timeline。
2. **类 Kontext 的音频修改**：没有“基于现有音频按自然语言重编辑”的模型任务；目前只是 JSON preset 和重生成入口。
3. **真实 ASMR 音效系统**：没有精选授权素材库、标签检索、自动切片、循环点和 AI 补充生成。
4. **可信双耳导演效果**：没有完整的近远频谱、早期反射、微延迟、HRTF 和空间自动化。
5. **自动听感 QA 与恢复**：没有 ASR 校验、音色一致性、遮蔽检测、候选评分和自动重试。
6. **声线卡与多 provider**：只有单一手工 voice pack；没有角色声线资产、适用语言、参考音频版本和 A/B provider 管理。
7. **完整交付格式**：没有 stems、MP3、SRT 和可复现的项目发布包。

## 6. 建议的完善顺序

以下是候选顺序，不是已批准 roadmap。建议下一对话先让用户批准“阶段 1”，再写中英文 spec 和实施计划。

### 阶段 1：真实导演指令与音频修改语义

目标：让工作台上每个声音指令都产生可听、可解释、可 A/B 的结果。

建议范围：

- 将导演动作分类为三类：Timeline 参数编辑、重新生成、基于已有音频的后处理/模型编辑。
- 动作结果必须记录 `sourceAsset`、操作类型、参数、provider、版本和新 `asset`，支持撤回与 A/B。
- `更柔` 应映射到真实的语音风格控制、候选重生成或模型音频编辑，而不是只降 2 dB。
- `更近` 应进入空间 DSP，至少包括距离 EQ、早期反射/干湿比和微延迟，而不是只改 gain。
- `停顿` 应成为结构化文本/音素停顿或可编辑 Timeline 间隔。
- 暂无真实实现的指令必须在 UI 中诚实标注或禁用，不能继续用名称掩盖兜底行为。

验收结果：对同一段源音频执行 `更柔`、`更近`、`右耳` 后，可通过盲听和波形/频谱指标辨认不同意图；操作历史可追踪，原资产不被覆盖。

建议把这个阶段命名为候选方向：**“生成与音频导演质量 V1”**。

### 阶段 2：语音质量、声线卡和 provider 策略

目标：先把最影响成品观感的人声做到稳定、可控。

建议范围：

- 建立与目标语言匹配、干净、近讲、低噪的参考语音集，避免把当前日语参考 + 中文目标当成正式方案。
- 将 `emotion`、`style`、`pace`、seed 和候选数量真实映射到 provider 或 prompt 策略。
- 建立声线卡：角色、语言、参考音频、真实转写、模型权重、适用风格、版本和授权来源。
- 保留 GPT-SoVITS 作为基线，与 IndexTTS2、CosyVoice 或 Fish Speech 做小样 A/B，而不是先重写整个适配层。
- 加入分句、呼吸点、标点/停顿规范和候选选择。

验收结果：固定测试脚本在多次生成中可懂度、音色一致性、停顿、耳语感和伪影达到约定阈值；声线和 provider 可以替换而不修改 Timeline DSL。

### 阶段 3：真实音效库优先，AI 生成补充

目标：用真实素材替换程序噪声，让摩擦、敲击、翻书、布料和环境声达到可发布水平。

建议范围：

- 先建立 8 类高频 ASMR 音效的授权素材包与元数据：材质、动作、强度、距离、声道、长度、循环点、响度、来源和许可证。
- 做本地检索、试听、裁切、循环、淡化和 Timeline 绑定。
- procedural provider 保留为离线占位或特殊合成层，不再作为默认成品来源。
- AI 音效生成只补足素材库没有的长尾描述，并把 provider/source 写进资产元数据。

验收结果：同一 Timeline 可一键用真实素材重建，循环处无明显接缝，近场细节和材质能被听辨，许可证可追踪。

### 阶段 4：空间与母带 DSP

目标：把“双耳导演”从 pan + gain 升级为可信的空间听感。

建议范围：

- 保留输入立体声，明确 mono、stereo 与 binaural 素材的混音规则。
- 增加距离 EQ、空气感/近讲低频、早期反射、微延迟和可控房间混响。
- 为移动轨迹做连续自动化，避免位置跳变。
- 实现真 LUFS 测量、true peak、soft limiter 和分轨 headroom 策略。
- HRTF 放在基础 DSP 可验收之后接入，避免它成为又一轮前置研究。

验收结果：近/中/远和左右/跨耳移动在耳机中稳定可辨；导出满足约定 LUFS 和 true peak，且没有硬削波。

### 阶段 5：自动质检、候选评分与自动恢复

目标：让长内容不是“生成成功就算成功”。

建议范围：

- 对语音运行 ASR，比较目标文本和转写。
- 检查时长偏差、静音、重复、削波、异常能量、语速和停顿。
- 使用 speaker embedding 或同类指标检查同角色音色漂移。
- 在混音层检查人声与背景遮蔽、响度和峰值。
- 对不合格 Clip 自动重试或保留多个候选，所有失败原因可解释。

验收结果：质量面板从“资产齐没齐”升级为“这一版能不能听”；典型坏样本能被稳定拦截，自动重试不会破坏历史版本。

### 阶段 6：补齐原始产品闭环

目标：在声音质量可信后，完成最初设计的创作与交付体验。

建议范围：

- 一句创意 -> 结构化策划 -> 脚本 -> Timeline 草案；
- Timeline 新增、删除、替换、排序、拖拽、播放头和范围试听；
- 声线卡和项目级角色管理；
- MP3、stems、SRT、manifest 与可搬迁项目包；
- 文件系统存储、资产清理、备份和本地 runtime 健康检查。

验收结果：新用户无需从 demo JSON 开始，可以从一句创意得到可编辑工程，并导出可继续制作或发布的一组完整资产。

## 7. 下一对话建议先做什么

在没有新 roadmap 批准前，建议接手对话只推进下面这个决策和设计，不要先写更多 bridge：

1. 与用户确认是否批准“生成与音频导演质量 V1”为下一阶段。
2. 选 3 个首批真实指令作为纵向切片，建议为 `更柔`、`更近`、`停顿`。
3. 为每个指令明确：输入资产、实际声音变化、执行引擎、是否重生成、版本记录、失败回退和 A/B 验收样例。
4. 盘点 GPT-SoVITS 可真实控制的参数与局限，再决定哪些指令走 TTS 重生成、哪些走 DSP、哪些需要新的音频编辑模型。
5. 写中英文 spec 和实施计划，经用户确认后再修改 `docs/ROADMAP.md`。

第一批实现不应同时追求所有模型。最有价值的纵向切片是：

> 选中一个真实 voice Clip -> 点击一个导演动作 -> 生成新版本资产 -> 原/新版 A/B 试听 -> 质量检查 -> 接受或撤回 -> 重新混音。

这条链路贯通后，后续增加其他动作或 provider 才是真正复用已有工程底座。

## 8. 需要用户决定的问题

- 下一阶段优先改善“人声表达与导演动作”，还是先改善“摩擦/敲击等真实音效”？本审计建议前者优先。
- 类 Kontext 音频编辑是否必须在第一阶段落地，还是允许首批动作由“可控重生成 + DSP”实现，但 UI 必须如实表达执行方式？
- 是否接受为高质量声线重新准备中文参考音频和真实转写？
- 新增 provider 的原则是质量优先、显存优先、速度优先，还是商业许可优先？
- 成品验收主要用主观 A/B，还是同步建立固定测试集和基础客观指标？本审计建议两者同时建立。

## 9. 风险提醒

- 不要再次把 adapter、mock、队列或 API 外壳独立升级成顶层产品步骤；只有它们服务于可听效果时才应实施。
- 不要在没有音频样例和 A/B 验收的情况下宣称“更柔”“更近”等能力完成。
- 不要让 provider 专有参数进入 Timeline DSL；应通过版本化的执行配置和资产 provenance 隔离模型变化。
- 不要覆盖原始生成资产。所有导演修改都应生成可追踪的新版本。
- 不要把现有 `target_lufs` 字段等同于已实现正式 LUFS 母带。
- 不要直接删除 procedural provider；它仍可作为离线演示、测试 fixture 和素材缺失时的诚实占位。
- 不要先做大而全 DAW。Timeline 编辑应围绕导演动作、版本比较和局部重生成逐步增强。
